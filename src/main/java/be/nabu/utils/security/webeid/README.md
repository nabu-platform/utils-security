# Web eID validation (initial scope)

Challenge handling follows the [Web eID system architecture](https://github.com/web-eid/web-eid-system-architecture-doc): the native application checks only the 44-to-128-character length and hashes the exact opaque string.

`WebEidValidator` accepts a structured `Token` (format, algorithm, unverifiedCertificate, signature), an exact configured HTTPS ASCII origin and the session's exact opaque challenge string (44 to 128 characters, not decoded or canonicalized). The caller parses JSON and rejects missing, duplicate or wrong-type fields; do not use attacker-controlled claims for authentication. Nabu must generate unpredictable challenges with at least 256 bits of entropy (padded Base64 is a suitable representation), bind them to the issuing browser session, enforce expiry and remove them atomically on use. This library verifies the signed origin/challenge bytes; it does not manage sessions or replay protection.

Configure a trusted, directly issuing intermediate CA certificate, an allowlist of acceptable authentication certificate policy OIDs, a `Clock`, and an OCSP endpoint and `Transport`. With OCSP enabled (recommended and required by default in application configuration), a missing endpoint is an error. Pass `new WebEidOcsp.HttpTransport()` for bounded HTTP requests (5-second connect/read, 64 KiB response, no redirects) or inject a transport for private networks/tests. The endpoint is configured by the server, never taken from a token or certificate AIA. Restrict the endpoint and network access at deployment to prevent SSRF. Only a server administrator should set `checkOcsp=false` for an explicitly authorized offline environment; the result is `NOT_CHECKED`, never `GOOD`. Persist or inspect `Result.ocspResponse` for OCSP evidence; it is available only when checked successfully.

Only web-eid:1.0, RS256, canonical unpadded base64url signature and certificate, and a direct issuer chain are supported. Other JWA algorithms (ES*, PS*, RS384/512), later formats, indirect chains, nonce-less OCSP services and responders on alternate trust paths fail closed. OCSP responses must carry the request nonce, a single matching certificate status, a fresh validity interval, and an issuer signature or an authorized directly issued responder certificate with OCSP signing EKU (independent of the user authentication policy allowlist). OCSP good status is not a substitute for PKIX path validation. Configure policy OIDs based on the intended national eID profile; never use a wildcard policy. This is a restricted RS256/direct-issuer/configured-responder implementation, not a claim of production readiness or Belgian eID compatibility. For deployments needing unsupported profiles, add explicit support and corresponding fixtures before enabling them.
